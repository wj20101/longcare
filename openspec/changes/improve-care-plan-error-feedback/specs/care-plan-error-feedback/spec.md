## Purpose

让护理人员在待护理计划进入详情失败时看到与实际错误类别一致、可理解的提示，并允许接口契约规定的可空资料正常加载。保留正常服务流程、手动重试及返回行为，避免把业务、服务端或数据问题统一归因于网络。

## ADDED Requirements

### Requirement: 护理详情展示准确的失败提示

系统 SHALL 区分护理订单详情加载时的业务失败、连接失败、超时、HTTP 错误、响应数据异常和未知失败。系统 MUST NOT 将所有失败统一描述为网络异常，也不得直接展示异常堆栈或原始 HTTP 错误体。

#### Scenario: 标准业务失败
- **WHEN** 接口返回可解析的业务失败及非空白 `resultMsg`
- **THEN** 页面以普通文本展示该业务提示，不替换成网络异常

#### Scenario: 业务提示为空
- **WHEN** 接口返回业务失败但 `resultMsg` 为空或仅含空白
- **THEN** 页面显示“护理计划加载失败，请稍后重试”，不得出现空白错误状态

#### Scenario: 连接失败或超时
- **WHEN** 请求被判定为连接失败或请求超时
- **THEN** 分别显示“无法连接服务器，请检查网络后重试”或“请求超时，请重试”

#### Scenario: 服务端 HTTP 失败
- **WHEN** 接口返回 HTTP 5xx
- **THEN** 显示“服务暂时不可用，请稍后重试”，不提示用户网络异常

#### Scenario: 其他 HTTP 失败
- **WHEN** 接口返回其他未成功的 HTTP 状态且没有已确认的业务错误契约
- **THEN** 显示“请求未成功，请稍后重试”，不猜测订单不存在或直接将 HTTP 状态当作业务码触发退出登录

#### Scenario: 数据或未知失败
- **WHEN** 响应无法解析、响应为空或成功响应缺少详情数据
- **THEN** 显示“服务数据异常，暂时无法加载护理计划”
- **AND** 未归类的其他请求异常显示“护理计划加载失败，请稍后重试”

### Requirement: 护理响应中的合法空值不阻断加载

系统 SHALL 接受护理列表及订单详情接口中已明确声明可空的现有资料字段为 `null` 或缺失，不因这些字段缺值而将整个有效响应判为请求失败。缺失资料 MUST NOT 被伪造为真实身份、坐标或服务数据，也不得绕过现有业务校验。

#### Scenario: 可空列表和详情资料
- **WHEN** 成功的护理响应中，可空的姓名、联系方式、身份证号、地址、性别、经纬度或项目名称为空，且其余内容有效
- **THEN** 列表或详情正常加载，缺失文字沿用现有空值展示约定
- **AND** 空坐标不转换为有效的零点坐标，身份与服务校验规则保持不变

#### Scenario: 非法数据仍失败
- **WHEN** 响应包含不符合契约的字段类型、损坏 JSON 或没有详情数据
- **THEN** 仍显示数据异常，不返回伪造的成功订单

### Requirement: 重试与页面生命周期保持正确

系统 SHALL 保留护理详情现有手动重试及返回路径，成功响应仍进入原有详情展示；会话失效继续遵循现有业务码规则。取消请求 MUST NOT 被当作加载错误展示。

#### Scenario: 失败后重试成功
- **WHEN** 用户在错误页点击重试，新的详情请求成功
- **THEN** 页面从错误状态进入加载状态，再显示本次详情，不残留旧提示

#### Scenario: 返回或取消
- **WHEN** 用户从错误页返回，或页面请求随生命周期取消
- **THEN** 返回行为不变，取消本身不产生错误提示或自动重试

#### Scenario: 既有会话失效
- **WHEN** 接口返回现有会话失效业务码 `1001` 或 `3002`
- **THEN** 保留全局会话失效行为，不因文案分类修改而绕过或重复引入另一套退出逻辑
