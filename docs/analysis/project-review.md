## 已知限制

### 数据库与缓存

[DatabaseModule](../../core/data/src/main/kotlin/com/ytone/longcare/di/DatabaseModule.kt) 仅允许从历史 v1/v2 重建。当前 v3 及后续版本缺少迁移路径时拒绝打开，保留原数据；下次 schema 升级必须提供保存本地进度与未上传照片记录的迁移及测试。

订单内存缓存已绑定会话失效，旧请求不能在换号后回填；照片上传结果先落盘再报告成功。COS 上传与本地数据库不能组成同一事务，上传后进程终止仍可能使重试再次上传；重复业务提交的服务端幂等性仍需结合接口契约判断。

### 计时与提醒

当前持久倒计时仍基于墙钟开始时刻与时长，用户或网络校时可改变显示与截止判断；本次恢复保留原截止，不引入跨重启单调时钟模型。精确授权不足时只做 inexact 降级，有声通知兜底也不能绕过系统/用户静音、勿扰或通知关闭。闹铃播放器的文件读取、异步准备和生命周期操作移至同一专用 Looper，服务侧设置准备与总生命周期预算，取消后不再接受旧播放请求。平台底层读取、启动或释放若自身阻塞，应用不能安全跨线程强制中断；主线程不等待，已进入底层的操作与物理声音停止不能承诺硬实时上限。释放抛出异常时，该进程内停止创建新播放器；只有能够排除旧播放仍在执行时才允许有声通知兜底。这是限制资源泄漏与重复响铃的保守策略，不能承诺不重启进程即可恢复底层播放。工作线程与待处理请求须保持有界，具体契约见[倒计时提醒诊断](../architecture/system-overview.md#闹钟计时与延迟诊断)。异步化不保证铃声加载更快，也不是荣耀现场问题根因已确认的证据。

### 厂商依赖

签到、签退、正式开始与持续上报使用 SDK 估计精度不超过 200 米的业务规则；100 米为优先目标，100～200 米可直接使用。这是项目策略，不是高德的真实误差保证；精度合格仍可能发生数据库误差等漂移。高德没有按米数限制回调的配置，质量筛选与有限补采由客户端执行。其他用户偶发现象缺少当时的 SDK 元数据，不能把本地模拟晚到回调或测试通过当作现场根因已证实。

服务端当前没有低精度异常签到/签退协议。客户端在 30 秒动作窗口内等待新回调并保留业务资料供重试，不能既拒绝所有不合格点又保证每次都能正常提交；不使用历史点、空坐标或伪造坐标兜底。后续若提供异常处理接口，须按服务端契约单独接入。定位方案和资源约束见[单次业务定位](../architecture/system-overview.md#单次业务定位)。

Vivo 小于 69 版本的 Home/锁屏停报反馈缺少确切版本、现场日志和 SDK 元数据，不能断言全部来自同一缺陷。当前修复覆盖可见时准备前台服务、实际启动确认、系统重建与前台恢复；厂商自启动、省电限制、强制停止及深度 Doze 仍可使采集或网络中断。现有小米、华为真机与隔离测试不替代现场 Vivo 验收，测试上报出口不代表护理接口线上已验收。

华为 STK-L21（Android 9 / EMUI 9.1）已区分两类中断：应用自动管理开启时，Home 后同 UID 线程进入 `__refrigerator` / `FROZEN`，前台通知仍存在；只将本应用改为手动管理并允许后台活动后，未再观察到该冻结，但高德原始回调空档仍在。小米 MI CC9e（Android 9）也曾出现约 96～115 秒空档，期间业务检查继续运行、elapsed/uptime 增量接近。不能仅凭通知、品牌或非 Doze 状态判断采集正常，也不能将这两机结果替代三星、HONOR、Vivo 现场验收。

2026-10-21 在华为上抓到高德 11.3.101 同一次调用的完整链路：网络层交付的新结果 tick 比已接受点前进 45.120 秒，内部小幅漂移过滤分支却返回旧对象，随后 observer 因旧 tick 重复而拒绝交付，应用没有收到该次原始回调。这次原因已确认，不再仅是时间戳门禁猜测；它不证明其他用户的全部空档都源于同一原因。取证使用有界、只读 JDWP，诊断窗口排除在性能统计外。公开参数、场景预设与关闭缓存均未找到控制该内部过滤链的受支持方法；仅 GPS 模式不适合室内护理。当前 [官方更新日志](https://lbs.amap.com/api/android-location-sdk/changelog) 未列出对此链路的修复。

同机 USB 充电、手动允许后台、30 秒 SDK 间隔、无调试器的十分钟锁屏对照中，将诊断包静默恢复阈值临时设为 30 分钟，确保观察不靠自动重建。11.3.101 窗口内仅 1 次原始成功回调和本地成功，固定分钟桶 1/10，最大空档（含尾部）589.580 秒，零客户端重建。约 23 毫秒即可从已收到的原始回调派发至本地隔离仓库，因此这段主要缺口在原始回调交付前。本地成功不是护理服务器确认，也不是地面位置真值；35 米是 SDK 估计精度。

同条件切换到 11.2.100 后，十分钟内有 18 次原始成功回调和旧规则本地成功，表面上分钟桶 10/10；但只有 1 个独立正源 tick，其余 17 次重复，最大源年龄 567.216 秒，公开 `time` 和 UTC 却持续前进，`isFixLastLocation` 仍为 false。因此不能通过回退 SDK 或只检查 UTC 声明达标。按正源 tick 去重、源龄不超过 60 秒和精度不超过 200 米等可见条件离线回放，两版均仅 1 个候选；这是日志回放，不是新规则的实际服务端成功。现已在 SDK 边界保留源 tick，复用既有质量规则核对源龄、动作单调起点与已派发 tick；未知值兼容原路径，不伪造新鲜度。

历史锁屏对照没有证明频繁销毁重建客户端或单独持有 CPU 锁能闭合全部空档。当前测试分支将原实例的 `stopLocation → setLocationOption → startLocation` 刷新改为有预算的客户端替换：后台或灭屏静默 45 秒、任意前后台状态静默 90 秒，或已有过期/重复来源证据且 90 秒没有通过基础质量与时效校验的新来源进展时，复用既有健康检查发起恢复。来源进展与业务合格点分开记录：前者仍要求合法坐标、时间、来源、可信度、正且有限的精度与采集阶段边界，只不应用业务 200 米精度上限；因此旧点之后持续收到新鲜但大于 200 米的点，不再被误判为来源停滞，这些点仍不得用于业务提交或上传。合格点也不等于接口成功，实际上传结果继续独立统计。每个订单采集启用阶段最多两次替换启动尝试；正常恢复之间至少 45 秒，一次新回调或单纯返回前台不会补满仍在运行阶段的预算；这限制了恢复尝试，不是长订单持续采集的保证。先使旧客户端失效并独立清理，再启动新客户端，旧回调不能进入新采集；新客户端配置或启动异常同样清理，最多使用剩余预算重试，启动失败耗尽后交给服务中断路径，不再把已停止实例保留为逻辑 active。配置读取期间的新鲜进展、暂停、换代或取消优先于迟到的恢复结果。该状态机与异常分支已有针对性回归用例，但离线测试不证明真实 SDK 的内部过滤被清空，更不等于一分钟有效上报已经达标。高德 `APSService` 保留为 SDK 配套组件，生产默认仍不重复启用 SDK 后台通知。

CPU 锁仍是未完成真机验收的实验候选：订单有效采集中每次就绪检查续租 180 秒 `PARTIAL_WAKE_LOCK`，15 秒检查持续续租意味着正常订单期间可能持续持锁，180 秒不是总时长上限；这与此前不常驻持锁的约束仍存在偏差。该超时通过应用主线程 Handler 按 uptime 释放；主线程阻塞或冻结会延迟执行，并非独立系统硬性墙钟租约。进程死亡仍由系统回收锁。本次不凭离线测试改变该租期或声称耗电优化完成。服务回归覆盖暂停/恢复、权限或隐私撤销、登出/换号、订单结束、协程取消及服务销毁后的释放，并验证获取失败不取消采样、后续检查可以重试；这些是生命周期与容错覆盖，不是实际耗电或锁屏采样收益证明。组合方案仍缺少对应构建的真机与功耗证据。旧 APK 和改进前候选的检查记录不能充当本次提交验收，历史方案、数据与版本边界见[历史测试资料](../../validation/location-sdk-foreground-20261022/README.md)。

三星熄屏停报、首次签退失败，以及荣耀长订单迟响的反馈缺少现场版本、权限和完整事件时间链。代码层另修复了休眠后动作预算失效、前台服务静默拒绝被当成功、旧会话迟到响应误登出新账号等独立缺陷；这些触发条件不能在缺少现场链路时直接归为相应品牌的实际根因。单调时间与计时起点修复也不能证明现场问题全部闭合。需要分别检查新鲜合格回调、客户端拒绝、网络响应与闹钟各阶段时间；没有回调或网络时，不能补传旧点冒充当前正确位置。

1.0.7 线上曾出现 SDK 成功的 GPS 回调被客户端 `TIME` 拦截（一次摘要为 13 次回调、12 次拒绝）。当前已统一源单调时间校验、会话水位与恢复边界，GPS UTC 偏移和校时回归通过；旧日志未保存接收时带符号差值，不能量化该次现场时钟偏差，也不能认定所有停报均由此引起。源 tick 缺失仍保守检查墙钟，后续用 `time` 证据区分具体分支。版本检查的成功响应空数据尚无“无更新”的契约依据；当前只结束本次任务并诊断，不再自动重试空响应。

清除空档自动重建后的最终版本，在小米 MI CC9e 上真实拔线锁屏固定五分钟：完整本地事件记录中原始回调、独立新源 tick 和本地成功均为 0，分钟桶 0/5、含首尾空档 300 秒；同一进程/客户端保留，没有重建或 `TIME` 拒绝。跨窗 elapsed/uptime 差给出窗口内 CPU 休眠下界约 264 秒（起点时钟映射误差约 52 毫秒）；电池历史确认轻量 Doze，不能由此把全部空档只归因于 Doze 或 SDK。重连后原客户端自然恢复；冷动作 0.886 秒/61 米，恢复后动作 2.840 秒/39 米且复用原客户端。华为 STK-L21 的接线 Home、进程中断后系统恢复、测试定位条件暂停恢复、换单归属和结束释放均通过，冷动作 1.315 秒/34 米、前台签退取点 3.141 秒/37 米并复用客户端。真实 SDK 与隔离上报计数不等于护理接口验收或地理真值，不替代三星现场；一分钟有效上报仍未达标。

小米同一 APK、相同 30 秒 SDK 配置、网络及系统定位提供器条件下，单独开启系统电池优化豁免的固定五分钟拔线锁屏窗口为原始回调 0 次、新源 tick 0 个、本地成功 0 次（0/5）；后续用户选择厂商“无限制”的窗口仍为 0/5。后一组起始人工标记记录为系统未豁免，但应用全程观测和重连时系统白名单均显示已豁免，因此只能证明两项放宽后的实际组合仍未达标，不能称为厂商单变量对照或直接推断设置联动原因。两组完整持久事件覆盖窗口，同一进程/客户端保留，CPU 休眠下界分别约 276/270 秒（起点映射误差约 54/55 毫秒）。这些结果不能排除其他机型/组合的限制。系统只启用网络定位，GPS 提供器关闭；SDK 的 HighAccuracy 配置不会替用户打开 GPS。高德[质量报告说明](https://a.amap.com/lbs/static/unzip/Android_Location_Doc/com/amap/api/location/AMapLocationQualityReport.html)建议使用包含 GPS 的系统模式，但 GPS 关闭只说明该来源不可用，不能据此认定全部空档的根因或宣称开启即可达标。后一组在锁屏窗口前还记录到亮屏、健康检查最大间隔 15.033 秒、最大休眠差 1 毫秒时已有 72.020 秒 SDK 原始回调空档；拒绝、失败与取消计数均为 0。故本轮同时确认 CPU 执行暂停和休眠前的 SDK 原始回调空档，没有证实业务任务被取消，也不能将两者合并为休眠单一原因。按用户最新要求保留本应用“无限制”作为后续基线，实测系统豁免为开启；隔离订单、服务、进程和测试资料已清理或恢复。

同环境的有界 CPU 锁隔离对照已确认 CPU 持续运行，但五分钟内有效本地成功只能确定为 1～3 次（仍不足 5 次），并再次进入轻量 Doze。持久计数、末次上传时间与健康摘要可界定结果；256 KB 主日志缓冲未保留完整中段，不能给出精确五桶或把少量保留行当成线程停摆。相关健康摘要最大检查间隔 15.139 秒、睡眠差 1 毫秒，不支持 UID 冻结结论；原始回调空档仍存在，但不足以把剩余问题只归因于 SDK。临时 CPU 锁与对照代码已删除，不直接加入生产常驻锁。高德说明已有前台服务时无需再调用 `enableBackgroundLocation`，因此也不复制第二套前台服务。后续结合完整本地留存、系统定位和网络限制逐项对照，不频繁重建或补传旧点。以上为真实 SDK、隔离订单与本地计数，未执行真实护理签到签退接口，不替代三星现场验收。

保留业务前台服务、在 Debug 中试用高德自身前台服务的同 APK 对照也未消除空档：小米两组固定五分钟拔线锁屏均为原始回调/新源 tick/本地成功 0，分钟桶均 0/5；端点证实 SDK 前台身份生效，进程/client 保留，CPU 休眠下界分别约 270/285 秒。华为接线验证另有 elapsed/uptime 均前进 164.700 秒的原始回调空档；进程中断后的自动恢复被系统以 `Stopping service due to app idle` 停止，可见页面显式恢复成功不能替代自动恢复验收。尚未证实 ROM 此次 idle 判定的具体原因。该试用默认关闭，不提升为生产修复；完整方案、固定窗口、原始证据及版本快照保存为测试产物，不以服务前台化宣称一分钟有效上报达标。

机型后台设置审查确认旧实现将 OPPO AppOp 66（安装包请求）误作后台弹页权限，且私有查询失败默认允许；当前已删除这些探测及未验证的厂商组件列表，设置入口具备安全回退并支持手动复查。小米真机还确认了强制 NEW_TASK 导致复用旧设置页的问题；Activity 调用已改为自然任务栈，并验证正确显示目标权限页。系统 Doze 豁免不等于厂商后台或休眠授权。三星休眠策略参考[官方说明](https://developer.samsung.com/mobile/app-management.html)，小米后台弹页与锁屏开关参考[官方说明](https://www.mi.com/uk/support/faq/details/KA-497760/)；具体菜单随 ROM 改变，现有小米、华为与通用 Android 测试不能替代三星、Vivo、OPPO、HONOR 或其他华为机型的现场验证。仍不能从品牌或“未豁免”单独推断停报根因。

权限交互审查进一步修正了取消建议即开始服务、拒绝后立即再次劝导、Activity 重建丢失待确认状态，以及定位捆绑通知申请的问题；通知渠道或渠道组关闭单独引导，独立全屏提醒设置文案限定 Android 14+。这些修改依据 [Google 权限建议](https://developer.android.com/training/permissions/requesting)、[特殊权限说明](https://developer.android.com/training/permissions/requesting-special) 与 [Compose Dialog](https://developer.android.com/develop/ui/compose/components/dialog)；具体“一次建议＋可手动恢复”及业务取消行为属于本项目交互选择，不能等同于 Google 对 OEM 后台设置的统一认证。

QLZ 当前使用默认正式环境；环境配置、单次 token、上报及结果页流程以 [QLZ 接入](../integrations/qlz-sdk.md) 为准，不再沿用旧测试模式说明。

当前 QLZ 弱 TLS、腾讯人脸 16 KB 对齐及 consumer rules 风险已获用户接受，正式构建继续告警。这不代表问题已修复；更新对应厂商包时重新验证，不能扩大为签名、Lint 或其他错误放行。具体门禁见[发布检查](../architecture/ci-quality-gates.md)。

R8 规则调整必须结合真实调用链、反射/JNI 与混淆产物验证，不依据历史候选列表直接删除。保留正式包实际需要的规则，不为测试专用 API 扩大保留范围。

### 腾讯人脸凭据

现有系统配置接口仍向客户端返回腾讯 AppSecret，客户端直接向腾讯换取 Access Token。当前缓解措施移除了普通配置持久化、内存缓存和 UI 状态中的 AppSecret，并限制了临时凭据与 SDK 回调的会话生命周期；这不能防止受控客户端在响应解析或换取 token 时提取密钥，也不保证 JVM 字符串安全擦除。

该高风险边界尚未闭合。完整修复需要服务端保管 AppSecret、代为请求腾讯凭据，并向客户端提供受限认证参数；本次保持后端 API 不变。厂商线上认证及真实账号切换仍需对应环境验收，离线单测不等同于腾讯服务端与真机验证。

### 性能采集

[BaselineProfileGenerator](../../baselineprofile/src/main/java/com/ytone/longcare/baselineprofile/BaselineProfileGenerator.kt) 当前等待包级根节点，随后执行滑动和返回，并将整个采集块包含到 Startup Profile；没有断言具体业务页面就绪，也不覆盖登录后的完整业务旅程。

因此，生成成功不能证明业务性能收益。只有实际开展性能优化时，再按目标页面调整采集、区分启动和交互路径，并用真机测量收益；这不是普通业务发布的新前置任务。

当前大屏方向约束和定位生命周期规则见[系统概览](../architecture/system-overview.md)，SDK/工具链以[技术栈](../architecture/tech-stack.md)为准。升级目标平台或修改相机、权限、前台服务时，再执行相应场景验证，不重复维护版本快照和通用验收矩阵。
