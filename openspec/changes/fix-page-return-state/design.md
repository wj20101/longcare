## Context

动机见 [proposal](proposal.md)。当前 `completeService` 已将栈整理为原 Home 加完成页，但完成页退出仍调用 `resetToHome`；选中项目清理只存在于顶部和底部按钮。销售详情有独立 entry ViewModel，返回时只补载空缓存；列表重新进入 Composition 后会无条件滚到顶部并搜索第一页。

该调整涉及 UI、导航注册和业务清理职责，需保留简短设计说明。Navigation 3 官方[状态保存文档](https://developer.android.com/guide/navigation/navigation-3/save-state)已通过 android-cli 核对：entry 在栈中时可以保留对应状态，退出不是重建来源页的理由。

## Goals / Non-Goals

**Goals:** 复用现有 pop 和页面生命周期，使三种完成页退出一致，详情数据新鲜、列表状态稳定。

**Non-Goals:** 不修改倒计时退出业务限制、服务计时/签到条件、H5 关闭用途或 SDK；不新增消息总线、返回结果邮箱、全局刷新框架或数据库迁移。

## Decisions

1. 完成页导航接口改为普通返回，三种退出入口调用同一 pop。既有 `completeService` 已移除服务过程页，故不会重新暴露前序操作；不改全局 `resetToHome`，以免影响登录及倒计时业务例外。
2. 在现有服务结束成功处理链中统一完成必要的选中项目清理，移除完成页按钮清理及仅为其存在的依赖。清理不能依赖即将销毁页面的协程；使用现有结束清理入口，保证成功状态发布与清理时序一致。接口失败保留重试数据，本地清理异常沿用现有错误记录，不重新提交已成功的结束请求；完成摘要继续使用现有明确参数和缓存。
3. 详情在当前 entry 进入 RESUMED 时调用现有详情查询，合并原首次加载/刷新分支，避免双发。复用请求取消及客户 ID 校验，不增加导航返回结果关联；保留 H5 同客户关闭复用来源的行为，去除确认无用的刷新标记或重复触发逻辑时同步测试。
4. 列表区分首次查询、条件变化与普通返回。利用现有 ViewModel 的条件、数据和最小加载状态避免同条件重载；不能仅用列表是否为空判断已加载。滚动重置仅跟随实际新查询，保留 `rememberLazyListState`。不把内存加载标志单独持久化，避免进程恢复后无数据却跳过查询；保留失败重试和新条件取消旧请求。

## Risks / Trade-offs

- [详情恢复增加一次查询] → 以 RESUMED 周期为界，重组不重查；不使用全局广播。
- [清理过早导致完成摘要缺失或失败不可重试] → 只在服务端成功后处理，验证摘要完整和失败数据保留。
- [仅改返回导致首页订单列表不刷新] → 核对既有首页恢复刷新路径；保留原 Home entry 的同时验证最新服务状态，不靠重建首页实现刷新。如需超出本次范围的改动，先报告。
- [列表去重阻断空结果、失败重试或进程恢复] → 分别覆盖成功空列表、失败重试、条件变化和数据丢失恢复。

## Migration Plan

无外部迁移。分服务完成、详情刷新、列表恢复三个小切片实现并测试；回滚对应切片即可。现有未提交导航改动作为当前基线保留，不覆盖或重做已完成工作。
