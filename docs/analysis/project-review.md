# 工程风险与维护边界

最后核对：2026-10-21（定位锁屏对照、恢复、签退取点与闹钟起点专项，其他风险非本轮全量复验）。本页只保留已知限制及其处理时机，不是待办清单或新增发布前置条件。业务流程见[产品概览](../product/overview.md)，模块和运行契约见[系统概览](../architecture/system-overview.md)，发布检查见[CI 与门禁](../architecture/ci-quality-gates.md)。

## 验证边界

- 定位的单元测试、设备权限与生命周期验证分别覆盖其验证范围；真机 SDK 与隔离上报计数不等于护理接口线上已验收，Debug 验证也不替代正式构建。这些结果不等于任何环境都不会漂移。定位契约见[定位会话与生命周期](../architecture/system-overview.md#定位会话与生命周期)。
- 按用户确认，不再保留长时静置、功耗或服务端数据对照验收任务。定位问题按实际复现和多次采集证据排查，不将这些已取消项目重新作为发布阻塞。
- QLZ 正式上传联调、NFC/R65C 实际读卡由用户于 2026-09-29 确认已通过，已关闭相关待验收项；本轮文档整理没有重新进行硬件测试。
- 普通 Android CI 与本地 `--full` 已通过 [run_jvm_tests.sh](../../scripts/quality/run_jvm_tests.sh) 选择全部 Android 模块的 Debug 单测及两个 Kotlin/JVM 模块测试。“普通 CI 不运行完整 JVM 业务单测”不再是当前事实；测试通过仍不代表全部线上流程或硬件组合均已覆盖。

## 已知限制

### 数据库与缓存

[DatabaseModule](../../core/data/src/main/kotlin/com/ytone/longcare/di/DatabaseModule.kt) 仅允许从历史 v1/v2 重建。当前 v3 及后续版本缺少迁移路径时拒绝打开，保留原数据；下次 schema 升级必须提供保存本地进度与未上传照片记录的迁移及测试。

订单内存缓存已绑定会话失效，旧请求不能在换号后回填；照片上传结果先落盘再报告成功。COS 上传与本地数据库不能组成同一事务，上传后进程终止仍可能使重试再次上传；重复业务提交的服务端幂等性仍需结合接口契约判断。

### 厂商依赖

签到、签退、正式开始与持续上报使用 SDK 估计精度不超过 200 米的业务规则；100 米为优先目标，100～200 米可直接使用。这是项目策略，不是高德的真实误差保证；精度合格仍可能发生数据库误差等漂移。高德没有按米数限制回调的配置，质量筛选与有限补采由客户端执行。其他用户偶发现象缺少当时的 SDK 元数据，不能把本地模拟晚到回调或测试通过当作现场根因已证实。

服务端当前没有低精度异常签到/签退协议。客户端在 30 秒动作窗口内等待新回调并保留业务资料供重试，不能既拒绝所有不合格点又保证每次都能正常提交；不使用历史点、空坐标或伪造坐标兜底。后续若提供异常处理接口，须按服务端契约单独接入。定位方案和资源约束见[单次业务定位](../architecture/system-overview.md#单次业务定位)。

Vivo 小于 69 版本的 Home/锁屏停报反馈缺少确切版本、现场日志和 SDK 元数据，不能断言全部来自同一缺陷。当前修复覆盖可见时准备前台服务、实际启动确认、系统重建与前台恢复；厂商自启动、省电限制、强制停止及深度 Doze 仍可使采集或网络中断。现有小米、华为真机与隔离测试不替代现场 Vivo 验收，测试上报出口不代表护理接口线上已验收。

华为 STK-L21（Android 9 / EMUI 9.1）已区分两类中断：应用自动管理开启时，Home 后同 UID 线程进入 `__refrigerator` / `FROZEN`，前台通知仍存在；只将本应用改为手动管理并允许后台活动后，未再观察到该冻结，但高德原始回调空档仍在。小米 MI CC9e（Android 9）也曾出现约 96～115 秒空档，期间业务检查继续运行、elapsed/uptime 增量接近。不能仅凭通知、品牌或非 Doze 状态判断采集正常，也不能将这两机结果替代三星、HONOR、Vivo 现场验收。

2026-10-21 在华为上抓到高德 11.3.101 同一次调用的完整链路：网络层交付的新结果 tick 比已接受点前进 45.120 秒，内部小幅漂移过滤分支却返回旧对象，随后 observer 因旧 tick 重复而拒绝交付，应用没有收到该次原始回调。这次原因已确认，不再仅是时间戳门禁猜测；它不证明其他用户的全部空档都源于同一原因。取证使用有界、只读 JDWP，诊断窗口排除在性能统计外。公开参数、场景预设与关闭缓存均未找到控制该内部过滤链的受支持方法；仅 GPS 模式不适合室内护理。当前 [官方更新日志](https://lbs.amap.com/api/android-location-sdk/changelog) 未列出对此链路的修复。

同机 USB 充电、手动允许后台、30 秒 SDK 间隔、无调试器的十分钟锁屏对照中，将诊断包静默恢复阈值临时设为 30 分钟，确保观察不靠自动重建。11.3.101 窗口内仅 1 次原始成功回调和本地成功，固定分钟桶 1/10，最大空档（含尾部）589.580 秒，零客户端重建。约 23 毫秒即可从已收到的原始回调派发至本地隔离仓库，因此这段主要缺口在原始回调交付前。本地成功不是护理服务器确认，也不是地面位置真值；35 米是 SDK 估计精度。

同条件切换到 11.2.100 后，十分钟内有 18 次原始成功回调和旧规则本地成功，表面上分钟桶 10/10；但只有 1 个独立正源 tick，其余 17 次重复，最大源年龄 567.216 秒，公开 `time` 和 UTC 却持续前进，`isFixLastLocation` 仍为 false。因此不能通过回退 SDK 或只检查 UTC 声明达标。按正源 tick 去重、源龄不超过 60 秒和精度不超过 200 米等可见条件离线回放，两版均仅 1 个候选；这是日志回放，不是新规则的实际服务端成功。现已在 SDK 边界保留源 tick，复用既有质量规则核对源龄、动作单调起点与已派发 tick；未知值兼容原路径，不伪造新鲜度。

先前每 90 秒静默允许恢复、回调再补充额度的版本曾在九分钟内重建四次，仍只有 6/9 固定分钟桶有本地成功；缩短业务检查或同步可见性未证明能消除 SDK 空档。现已改为同 owner 连续启用阶段最多自动重建一次，成功、错误及重建首点不补额度；保留监听器和既有诊断，真实暂停恢复或新 owner 才重置。此上限避免恢复循环，不是 SDK 根因修复；一分钟有效上报尚未达标，禁止以补传旧点、刷新采样时间或频繁重建声明通过。

正常 90 秒静默策略、每阶段最多一次恢复及源时间/去重校验的六分钟锁屏验证，收到 2 个新源 tick 并产生 2 次本地成功，分钟桶 2/6，最大原始回调空档（含窗口尾部）252.680 秒；发生 1 次自动重建，后续持续空档没有再重建。估计精度均为 38 米，仍未达到每分钟一次有效上报。该窗口在最后的恢复源 tick 边界补充之前完成；补充仅收紧暂停后的旧来源拒绝，另以最终包验证恢复流程，不能把它宣称为 SDK 静默修复。

最终包在同机重新验证：三分钟锁屏收到 2 个新源 tick 和 2 次本地成功，分钟桶 2/3，最大空档 100.964 秒；仍未达标。无持续客户端时动作取点 1.325 秒，锁屏恢复后首次动作取点 0.282 秒，后者复用同客户端；系统定位重新开启后约 9.901 秒、锁屏进程中断后约 18.890 秒恢复同订单新点本地上报。换单未出现旧订单串报，结束后服务和客户端释放；测试结束还原本应用自动启动管理与原 GPS/网络定位状态，清除隔离探针状态。以上均为充电室内的真实 SDK、隔离订单及本地计数，真实护理签到签退接口和其他品牌现场仍未验证。自动恢复曾被 ActivityManager 以 `restricted / app idle` 在业务启动前停止，当前通过不代表能绕过厂商限制。

三星最新代码的锁屏漏报及仅响铃反馈同样缺少现场订单、系统版本与权限状态。代码审查确认重复节流、请求缺少总时限、冷缓存跳过初始化、授权未续查/重排、重复通知发布及弹页失败后删除唯一提醒等缺口；当前实现已统一采样节奏、请求预算和页面恢复入口，去除静态倒计时服务、直接弹页回退及提前结束签退的路径。首次排程的异步读取改由 ViewModel 持有，避免初始化期间 Home/锁屏取消读取而漏排闹钟；可见性只管理显示刷新。这些代码证据不等于三星现场根因已全部证实。Android 14+ 全屏提醒权限、通知渠道和厂商策略仍可能阻止自动弹页；诊断记录实际授权、渠道重要性、锁屏状态及上传耗时，不绕过系统授权。旧排程没有账号标记时，仅在已有恢复记录与当前账号/订单一致且服务端确认执行中后迁移；缺少证据或五秒验证预算内不可用时不会响铃，重新进入订单会恢复排程。

三星熄屏停报、首次签退失败，以及荣耀 15/20 分钟订单迟响 2/3 分钟的反馈尚无现场版本、权限和事件时间链。现已修复代码可证明的问题：电池优化已豁免时仍跳过 Doze 恢复、返回前台未立即复核采集条件、签退借用已静默客户端而消耗完整等待预算，以及正式开始后延迟保存/并发覆盖计时起点。回归测试先复现这些缺陷再验证修复；没有发现可直接证明“订单越长按比例延迟”的计时算法，不能把起点修复等同于荣耀迟响根因全部闭合。需要用截止时间、实际排程模式、广播到达和播放启动的现有诊断链区分剩余原因；现有实现尚不能保证每分钟至少一次正确上报；缺少新鲜合格回调、无网络或系统冻结时，不能补传旧点冒充当前正确位置。

机型后台设置审查确认旧实现将 OPPO AppOp 66（安装包请求）误作后台弹页权限，且私有查询失败默认允许；当前已删除这些探测及未验证的厂商组件列表，设置入口具备安全回退并支持手动复查。小米真机还确认了强制 NEW_TASK 导致复用旧设置页的问题；Activity 调用已改为自然任务栈，并验证正确显示目标权限页。系统 Doze 豁免不等于厂商后台或休眠授权。三星休眠策略参考[官方说明](https://developer.samsung.com/mobile/app-management.html)，小米后台弹页与锁屏开关参考[官方说明](https://www.mi.com/uk/support/faq/details/KA-497760/)；具体菜单随 ROM 改变，现有小米、华为与通用 Android 测试不能替代三星、Vivo、OPPO、HONOR 或其他华为机型的现场验证。仍不能从品牌或“未豁免”单独推断停报根因。

权限交互审查进一步修正了取消建议即开始服务、拒绝后立即再次劝导、Activity 重建丢失待确认状态，以及定位捆绑通知申请的问题；通知渠道或渠道组关闭单独引导，独立全屏提醒设置文案限定 Android 14+。这些修改依据 [Google 权限建议](https://developer.android.com/training/permissions/requesting)、[特殊权限说明](https://developer.android.com/training/permissions/requesting-special) 与 [Compose Dialog](https://developer.android.com/develop/ui/compose/components/dialog)；具体“一次建议＋可手动恢复”及业务取消行为属于本项目交互选择，不能等同于 Google 对 OEM 后台设置的统一认证。

QLZ 当前使用默认正式环境；环境配置、单次 token、上报及结果页流程以 [QLZ 接入](../integrations/qlz-sdk.md) 为准，不再沿用旧测试模式说明。

当前 QLZ 弱 TLS、腾讯人脸 16 KB 对齐及 consumer rules 风险已获用户接受，正式构建继续告警。这不代表问题已修复；更新对应厂商包时重新验证，不能扩大为签名、Lint 或其他错误放行。具体门禁见[发布检查](../architecture/ci-quality-gates.md)。

R8 规则调整必须结合真实调用链、反射/JNI 与混淆产物验证，不依据历史候选列表直接删除。保留正式包实际需要的规则，不为测试专用 API 扩大保留范围。

### 腾讯人脸凭据

现有系统配置接口仍向客户端返回腾讯 AppSecret，客户端直接向腾讯换取 Access Token。当前缓解措施移除了普通配置持久化、内存缓存和 UI 状态中的 AppSecret，并限制了临时凭据与 SDK 回调的会话生命周期；这不能防止受控客户端在响应解析或换取 token 时提取密钥，也不保证 JVM 字符串安全擦除。

该高风险边界尚未闭合。完整修复需要服务端保管 AppSecret、代为请求腾讯凭据，并向客户端提供受限认证参数；本次保持后端 API 不变。厂商线上认证及真实账号切换仍需对应环境验收，离线单测不等同于腾讯服务端与真机验证。

### 性能采集

[BaselineProfileGenerator](../../baselineprofile/src/main/java/com/ytone/longcare/baselineprofile/BaselineProfileGenerator.kt) 当前等待包级根节点，随后执行滑动和返回，并将整个采集块包含到 Startup Profile；没有断言具体业务页面就绪，也不覆盖登录后的完整业务旅程。

因此，生成成功不能证明业务性能收益。只有实际开展性能优化时，再按目标页面调整采集、区分启动和交互路径，并用真机测量收益；这不是普通业务发布的新前置任务。

### 模块与平台

多数 route UI 和销售组装仍在 `:app`，`SalesViewModel` 职责较集中。后续修改相关功能时按需拆分，保持行为和导航栈测试，不为收尾强制进行全量模块迁移。

当前大屏方向约束和定位生命周期规则见[系统概览](../architecture/system-overview.md)，SDK/工具链以[技术栈](../architecture/tech-stack.md)为准。升级目标平台或修改相机、权限、前台服务时，再执行相应场景验证，不重复维护版本快照和通用验收矩阵。
