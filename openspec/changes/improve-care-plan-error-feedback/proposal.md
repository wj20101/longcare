## Why

待护理计划进入详情时，客户端将 HTTP、超时、响应解析等异常统一显示为“网络异常”，用户无法据此判断如何处理。在线护理接口还存在允许为空、客户端却声明非空的字段，需要同时修正契约不一致，避免仅替换文案而保留加载失败。

## What Changes

- 护理订单详情复用现有请求错误分类，分别提示业务失败、连接失败、超时、HTTP、响应数据异常和未知失败；业务提示为空时提供兜底。
- 对齐护理列表及详情相关模型中在线 Schema 明确允许为空的现有字段，并在展示和本地映射处处理缺失值；不把无效数据或请求失败伪装成成功。
- 保留现有重试、返回、会话失效处理和服务执行规则，补充接口解析、错误提示与恢复回归测试。
- `planId` 遗漏仅作为待核实问题记录；没有运行证据和另行确认前不改变请求、路由或缓存标识规则。
- 不新增错误处理框架、全局自动重试、HTTP 错误体猜测解析或全应用文案批量替换。

## Capabilities

### New Capabilities

- `care-plan-error-feedback`: 护理计划详情按实际错误类别提示，以及护理接口允许空值的正确处理和重试恢复。

### Modified Capabilities

无。现有主规格未定义该错误展示能力。

## Impact

- 主要涉及 `:core:ui` 订单详情 ViewModel/提示资源、`:core:model` 护理响应模型、`:core:data` 对应本地映射，以及受字段可空性影响的直接 UI 消费点和测试。
- 复用 `:core:common` 的 `ApiRequestException` 和 `ApiResult`，不改变 API 路径、JSON key、业务成功码及网络依赖。
- 不修改 Room schema、发布配置、权限或三方 SDK；不新增敏感日志。真实失败原因仍需实际请求证据，不将契约风险断言为本次故障根因。
