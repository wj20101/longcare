## Context

参见 [proposal.md](proposal.md) 的动机。本 change 是跨越全部模块、构建路径和质量域的评估工作，不是某个功能模块的代码修改。

当前工程事实决定了体检不能只运行一个 Gradle 任务：

- `settings.gradle.kts` 声明单 APK、`:baselineprofile`、五个 `:core:*` 和六个 `:feature:*` 模块，另有 included build `build-logic`。
- Android CLI 能识别 `app` 的 `debug`、`release`、`nonMinifiedRelease`、`benchmarkRelease` 变体，以及对应 Baseline Profile 目标；纯 JVM 模块仍需从 Gradle 设置和任务补充清单。
- 仓库已有 local-fast、ci-required、release-required 和 observability-only 分层，但 `quality_gate_registry.json`、实际脚本和 workflow 的覆盖面并不完全相同，必须交叉核对。
- 普通 Android CI 是 build-only 基线，不覆盖全部业务单测、instrumentation 或用户旅程；生产 Release 又因已知厂商问题有意 fail-closed。
- Android 官方质量框架把应用质量分为核心价值、用户体验、技术质量、隐私与安全；技术质量进一步强调稳定性、启动与渲染性能、资源使用、包体和健康发布。LongCare 还需要纳入大屏连续性、复杂平台生命周期及闭源 SDK 风险。
- 仓库不维护一次性审计报告；原始证据必须留在 `build/reports/` 或 CI artifact，长期事实进入现有真相文档，整改通过后续独立 OpenSpec change 管理。

## Goals / Non-Goals

**Goals:**

- 建立一次可复现的全项目健康快照，不遗漏未运行或不可运行的检查。
- 用统一状态、严重度和证据强度区分新增回退、既有风险、预期阻断与环境限制。
- 先复用现有门禁和测试，再通过代码/配置审查与受控运行时验证补齐盲区。
- 给出能独立实施、独立验证和独立回滚的后续整改切片。
- 将确认后的长期事实合并回现有文档，保持代码、门禁、测试与文档一致。

**Non-Goals:**

- 不在体检 change 内修复发现项、升级依赖、迁移模块、调整业务行为或改变发布策略。
- 不把生产门禁改绿，不修改 allowlist、waiver、签名 fallback 或厂商二进制来掩盖失败。
- 不在未经授权时访问真实用户数据、生产后端、Play Console、私有仓库或需要真实凭据的服务。
- 不承诺仅凭静态分析证明所有闭源 AAR、真机硬件路径或线上稳定性完全健康。
- 不创建新的长期审计报告、进度日志或 findings 文档。

## Decisions

### 1. 使用覆盖矩阵而不是单一健康分数

体检先建立“评估域 × 模块/构建路径/关键旅程”的覆盖矩阵。每个检查项至少保存以下字段：

| 字段 | 含义 |
|---|---|
| Baseline | commit/工作树、日期、工具链与设备 |
| Scope | 模块、变体、组件、集成或用户旅程 |
| Check | 检查目标与适用条件 |
| Evidence | 命令/事实来源、退出状态、原始证据位置 |
| Result | `PASS`、`FAIL_NEW`、`KNOWN_RISK`、`EXPECTED_FAIL_CLOSED`、`UNVERIFIED`、`ENVIRONMENT_ERROR` 或 `N/A` |
| Strength | 静态审查、自动化测试、模拟器、真机或线上证据 |
| Priority | `P0`、`P1`、`P2` 或仅观察 |
| Follow-up | 责任边界、补证条件或后续 change 建议 |

选择矩阵是因为单一分数会让“多数检查通过”掩盖一个生产安全阻断，也无法表达未验证区域。备选方案是复用 Android App Performance Score 作为总分；该分数只适合性能子域，因此保留为性能证据之一，不作为项目总健康结论。

### 2. 合并项目原生基线与 Android 官方基线

项目原生基线来自代码、Gradle/Manifest、测试、质量脚本、workflow 和当前真相文档；Android 平台相关判断通过 `android docs search/fetch` 核对官方现行资料。两者映射为以下评估域：

1. 产品与关键旅程契约。
2. 构建、工具链、依赖和供应链。
3. 模块架构、API 边界和可维护性。
4. Kotlin/协程、状态、错误处理和资源生命周期。
5. 测试清单、测试可信度和 CI 实际执行覆盖。
6. Android 组件、Intent、权限、隐私、网络与数据安全。
7. Room/DataStore/WorkManager、网络契约、文件和会话一致性。
8. 启动、渲染、包体、内存/电量/网络、Baseline/Startup Profile。
9. 手机、大屏、折叠、多窗口、方向与状态恢复。
10. Debug、验收和生产发布安全及文档一致性。

备选方案是只运行仓库现有脚本；这会遗漏脚本尚未覆盖的测试真实性、用户旅程、运行时性能和文档漂移，因此不采用。

### 3. 按成本与风险分阶段执行，并持续记录失败

执行顺序为：基线与清单 → 便宜的静态/脚本门禁 → 全模块编译和单测 → Lint/验收与发布检查 → 安全/架构深查 → 受控模拟器或真机旅程 → 性能与自适应验证 → 汇总。单项失败只记录状态，不中止后续无依赖检查；只有可能泄露数据、改变外部状态或破坏工作树的条件才停止。

这种顺序能先发现环境和配置问题，再投入昂贵的设备/性能时间。备选方案是直接运行最大 Gradle/Release 任务；它会在首个已知阻断处停止，产生昂贵但不完整的覆盖。

### 4. 复用现有入口，但验证“声明覆盖”与“实际覆盖”一致

体检以 `preflight_local.sh`、质量 registry、各 `verify_*.sh`、Android CI/Release、专项 workflow、Gradle 测试任务和 Android CLI 为入口，不在本 change 新建第二套质量框架。同时检查：

- registry 是否遗漏实际阻断门禁，文档是否把未执行检查描述成已执行；
- 每个源码集和测试类型是否有可发现、可启动且有断言价值的任务；
- Debug、验收、production、benchmark/profile 的配置和产物语义是否被正确区分；
- 失败日志能否指向责任边界，而不是只能得到一个聚合红灯。

若发现需要新增守卫或 runner，只把它定义为后续独立 change。备选方案是在本 change 顺手修复体检工具，会混淆“被测对象”和“测量工具”的基线，因此不采用。

### 5. 证据强度与结论置信度分开记录

静态代码审查可以确认明显契约或配置问题，但不能替代运行时行为；模拟器可以验证可重复交互，但不能替代 NFC、蓝牙、相机质量、厂商 native 库和性能真机证据；线上 Android Vitals 又依赖外部访问。因此每个结论同时记录证据类型和高/中/低置信度。

对于稳定性、性能和关键业务旅程，优先顺序是可复现自动化证据，再补代表性真机或线上指标。缺失的证据标记为 `UNVERIFIED`，不能通过提高静态推断措辞来补齐。

### 6. 运行时体检采用受控环境和显式授权边界

默认使用启用本地 mock 的 Debug 构建或明确的 acceptance 配置；可能触达真实后端、上传图片、产生定位/评估记录、操作账号或需要生产凭据的步骤不自动执行。Android CLI 用于设备发现、安装/运行、布局检查和截图；NFC、R65C、QLZ、真实相机、人脸与定位等硬件链路只在合适设备与测试账号可用时验证。

备选方案是为了提高覆盖率直接使用仓库默认的真实后端 Debug 路径；该方案可能产生不可逆外部状态并污染体检证据，因此不采用。

### 7. 已知 production fail-closed 保持风险与执行语义双重状态

已记录的 QLZ 固定测试配置、弱 TLS、腾讯人脸 16 KB 对齐及 consumer rules 问题仍按 P0 风险保留；当生产门禁因此失败时，执行结果记为 `EXPECTED_FAIL_CLOSED`，表示守卫工作正常，而不是表示项目健康。若同一路径出现不同根因，则另记 `FAIL_NEW`。

这样可以同时避免两种错误：把预期阻断当成回退，以及把“阻断按预期发生”误报成生产可发布。

### 8. 原始报告临时保存，长期结论进入既有真相集

命令输出、矩阵、截图、Lint、测试、benchmark 和 APK 分析结果写入 `build/reports/project-health/<baseline-id>/` 或已有报告目录，并保持不跟踪。最终只把仍会影响后续决策的事实同步到对应现有文档；每个整改建议使用单独 OpenSpec change，而不是在路线图中塞入执行细节。

备选方案是提交完整审计报告；报告会随代码快速失效并与现有文档形成第二真相源，因此不采用。

## Risks / Trade-offs

- **[全项目范围导致耗时长或资源不足]** → 先完成静态、构建和测试基线；设备、性能与外部证据独立标记状态，允许补证但不隐藏缺口。
- **[体检期间代码继续变化导致证据失效]** → 固定 baseline commit/工作树摘要；发现工作树变化时停止合并结论并重新标识基线。
- **[聚合任务首个失败掩盖其他问题]** → 按检查项独立执行并记录退出状态；只在确有依赖时跳过后续项。
- **[运行时检查污染真实数据或泄露凭据]** → 默认 mock/acceptance，输出脱敏；需要真实系统时先取得单独授权。
- **[闭源 SDK 无法完整审计]** → 结合 AAR/Manifest/native/consumer rules 静态证据与真实设备旅程，剩余部分明确为外部证据缺口。
- **[文档更新把短期噪声固化]** → 只有复现稳定、影响后续维护的事实进入真相文档；原始结果保留在忽略目录或 CI artifact。
- **[体检演变成大规模修复]** → tasks 只允许评估、分类、补证和事实同步；所有代码或门禁修复拆为新的 change。

## Migration Plan

1. 在固定基线创建临时证据目录并生成模块、变体、测试、组件、依赖、门禁与文档清单。
2. 分阶段执行可自动化检查，持续更新覆盖矩阵；失败不阻断无依赖项目。
3. 在安全前提下运行可用的模拟器/真机、关键旅程和性能检查，其余项记录补证条件。
4. 复核所有失败分类和严重度，把长期事实同步到现有文档，并为整改生成独立 change 建议。
5. 严格验证本 OpenSpec change；用户评审体检结论后再归档。

本 change 不部署运行时代码。若需回滚，只需撤销本次长期文档同步并删除忽略目录中的临时证据；既有应用产物和发布守卫不受影响。

## Open Questions

- 是否能在执行阶段提供至少一台覆盖相机/NFC/蓝牙/定位的代表性真机和受控测试账号；不可用时对应旅程保持 `UNVERIFIED`。
- 是否能访问 Play Console Android Vitals、线上崩溃/ANR 和设备分布；不可用时只给出本地与仓库证据，不推断线上健康度。
- 是否具备验收 Release 所需的受控配置和签名材料；缺失时只验证不需秘密的守卫、配置和可构建路径。
